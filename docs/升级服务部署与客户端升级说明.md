# 升级服务部署与客户端升级说明

ZungMail 的在线升级由两部分组成：

- **升级服务**（`src/ZungMail.UpdateServer`）：自托管的 ASP.NET Core 服务，自带后台管理页。开发者在这里上传完整安装包、填写版本信息并发布；客户端从这里检测和下载。
- **客户端升级链路**：配置服务根地址 → 启动数分钟后自动检测（也可手动检测）→ 状态栏显示新版本 → 用户点击下载 → 校验 SHA256 → 引导关闭客户端并运行新安装包 → 装完自动重新打开客户端。

> 升级只替换程序文件。本地数据目录（数据库、设置、模板、账户凭据、`.eml`）不参与升级，覆盖安装不会删除它们。

---

## 1. 接口约定

客户端只配置**服务根地址**（域名、IP、可带端口与路径前缀），接口路径内置在 `ZungMail.Update.Protocol`，服务端与客户端共用同一份定义。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/update/ping` | 探测服务，返回协议版本与服务名 |
| GET | `/api/update/check?current=1.0.0&channel=stable&os=windows&arch=x64` | 检测新版本；无更新时 `update` 为 `null` |
| GET | `/api/update/download/{id}` | 下载安装包，支持 `Range` 断点；响应头 `X-Checksum-Sha256` |
| POST | `/api/feedback` | 接收客户端问题反馈（公开，不需要管理员会话） |
| GET | `/healthz` | 健康检查（数据目录可写、已发布版本数、反馈条数与反馈目录可写） |

检测响应示例：

```json
{
  "protocol": 1,
  "serverTime": "2026-10-19T08:12:01Z",
  "update": {
    "id": "stable-1.1.0",
    "version": "1.1.0",
    "channel": "stable",
    "notes": "修复若干问题。",
    "mandatory": false,
    "minVersion": null,
    "fileName": "ZungMail-1.1.0-win-x64-selfcontained-setup.exe",
    "size": 104857600,
    "sha256": "d84a82e6…",
    "publishedAt": "2026-10-19T08:12:01Z",
    "downloadUrl": "/api/update/download/stable-1.1.0"
  }
}
```

约定：

- 版本号必须形如 `1.2.3` 或 `1.2.3.4`，可带 `-beta.1` 后缀；预发布版本低于同号正式版。
- `downloadUrl` 返回相对路径，客户端按配置的根地址拼接，因此反向代理加子路径也能用。
- `channel` 默认 `stable`，客户端可在设置里切到 `beta`；服务端按渠道筛选择优返回最高版本。
- 协议版本不兼容时递增 `protocol`，客户端会提示“升级服务协议版本过新”。

后台管理接口（需要登录 Cookie，仅管理页使用）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST / GET / DELETE | `/api/admin/session` | 登录 / 查询会话 / 退出 |
| GET / POST | `/api/admin/releases` | 版本列表 / 上传安装包（multipart，草稿） |
| PUT | `/api/admin/releases/{id}` | 编辑版本号、渠道、说明、强制标记、最低版本 |
| POST | `/api/admin/releases/{id}/publish` | 发布 |
| POST | `/api/admin/releases/{id}/unpublish` | 下线 |
| DELETE | `/api/admin/releases/{id}` | 删除记录与安装包 |
| GET | `/api/admin/settings` | 数据目录、口令来源、客户端地址提示 |
| POST | `/api/admin/password` | 修改管理员口令 |
| GET | `/api/admin/feedback` | 反馈列表（时间倒序，只带摘要） |
| GET | `/api/admin/feedback/{id}` | 单条反馈详情（完整描述、环境摘要、日志） |
| GET | `/api/admin/feedback/{id}/log` | 下载该条反馈的日志（`<编号>.log`，纯文本附件） |
| DELETE | `/api/admin/feedback/{id}` | 删除反馈记录与日志文件 |

### 1.1 问题反馈接口

客户端在「设置 → 反馈」里提交，请求体是 JSON（上限 1 MB，超出返回 413）：

```json
{
  "category": "malfunction",
  "description": "发送带大附件时进度条卡在 99%",
  "contact": "ops@forwarder.cn",
  "clientVersion": "1.0.0",
  "channel": "stable",
  "environment": "客户端版本：1.0.0\n操作系统：…",
  "log": "2026-10-19 10:00:01 [INFO] …",
  "logTruncated": false,
  "submittedAt": "2026-10-19T10:02:11+08:00"
}
```

- `category` 取值：`malfunction`（功能异常）/ `question`（使用咨询）/ `suggestion`（改进建议）/ `other`；未知值统一归为 `other`。
- `description` 必填，空白返回 400，上限 4000 字。
- `contact` 与 `log` 可为空；`environment` 由客户端生成，只含版本、系统与规模统计。
- 成功返回 `{"id":"fb-20261019-001","receivedAt":"…"}`，编号按天累计，管理页与日志里都用它定位。
- 同一来源 IP 每小时上限默认 10 条（超出 429，带 `Retry-After`），可用 `UPDATESERVER_FEEDBACK_PER_HOUR=0` 关闭限流。
- 落盘为 `data/feedback/<编号>.json`（元数据 / 描述 / 环境）与 `<编号>.log`（日志）；超过 `UPDATESERVER_MAX_FEEDBACK_RECORDS`（默认 200）条时淘汰最旧记录。
- 客户端提交前会把日志里的邮箱替换为 `<email>`、`password=` / `secret=` / `Authorization:` 一类凭据替换为 `<redacted>`，只取最新日志文件末尾 ≤512 KB。

## 2. Docker 部署

### 2.1 直接使用 compose（推荐）

```bash
cd packaging/update-server
# 先把 compose 里的 UPDATESERVER_ADMIN_PASSWORD 改成强口令
docker compose up -d --build
```

- 管理页：`http://<主机>:8080/`
- 数据卷：`update-data`（版本记录 `releases.json`、安装包 `packages/`、管理员口令哈希 `admin.json`）
- 健康检查：容器内 `curl -fsS http://127.0.0.1:8080/healthz`
- 重建容器不影响数据：`docker compose down && docker compose up -d` 仍挂载同一卷。

### 2.2 手工构建

```bash
docker build -f packaging/update-server/Dockerfile -t zungmail-update-server:1.0.0 .
docker run -d --name zungmail-update-server \
  -p 8080:8080 \
  -e UPDATESERVER_ADMIN_PASSWORD='请换成强口令' \
  -v zungmail-update-data:/data \
  zungmail-update-server:1.0.0
```

### 2.3 不使用 Docker（Windows / Linux 直接跑）

```powershell
dotnet publish src/ZungMail.UpdateServer/ZungMail.UpdateServer.csproj -c Release -o out/update-server
$env:UPDATESERVER_ADMIN_PASSWORD = '请换成强口令'
$env:UPDATESERVER_DATA = 'D:\ZungMailUpdateData'
dotnet out/update-server/ZungMail.UpdateServer.dll --urls http://0.0.0.0:8080
```

### 2.4 反向代理与子路径

Nginx 示例（HTTPS 由 Nginx 终止）：

```nginx
location /updates/ {
    proxy_pass http://127.0.0.1:8080/;   # 注意结尾斜杠：去掉 /updates 前缀
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 2g;
    proxy_read_timeout 600s;
}
```

此时客户端填 `https://example.com/updates`。也可以不改前缀，直接设 `UPDATESERVER_PATH_BASE=/updates` 让服务自己处理。

- `client_max_body_size` 必须大于安装包体积，否则上传会被代理直接拒绝。
- `proxy_read_timeout` 覆盖大文件上传/下载时间。
- 服务已信任 `X-Forwarded-For / X-Forwarded-Proto`，登录限流按真实来源 IP 计数，会话 Cookie 的 `Secure` 也按真实协议判断。

### 2.5 管理员口令

优先级：

1. 环境变量 `UPDATESERVER_ADMIN_PASSWORD`：只读，管理页不允许在线改口令（改环境变量后重启）。
2. 数据目录 `admin.json`（PBKDF2-SHA256 哈希）：首次启动未提供环境变量时自动生成随机口令，明文写在 `data/initial-admin-password.txt`，登录后请在管理页改口令，文件会自动删除。
3. 修改口令后所有会话立即失效，需要用新口令重新登录。

生产建议：

- 用 Docker secret / 环境变量注入强口令，不要把口令写进镜像。
- 定期备份数据卷（`releases.json` + `packages/`）。
- 对外必须走 HTTPS：客户端允许 http 是方便内网自托管，公网明文传输会被中间人替换安装包（客户端会校验 SHA256，但仍应使用 TLS）。

## 3. 管理页使用

1. 打开 `http://<主机>:8080/`，输入管理员口令。
2. 「上传安装包」选择完整安装包（`.exe` / `.msi` / `.zip`），版本号会尝试从文件名（如 `ZungMail-1.2.0-win-x64-selfcontained-setup.exe`、`ZungMail-1.2.0-x64.msi`）自动带出，填写更新说明；需要时勾选「强制更新」或填写「最低可升级版本」。
3. 上传成功为**草稿**，客户端看不到。检查无误后点「发布」。
4. 发布后「客户端配置」卡片会显示客户端应填的根地址；右侧能看到每个版本的下载次数。
5. 需要撤回时点「下线」（客户端立即检测不到，但已下载的客户端不受影响）；需要彻底清理时点「删除」（记录与安装包一起删除，旧下载地址返回 404）。
6. 「修改口令」仅在最开始未用环境变量提供口令时可用。
7. 顶部「用户反馈」页签列出客户端提交的反馈（时间倒序，带分类、客户端版本与描述摘要）；点「查看详情」展开完整描述、系统环境与日志，「下载日志」把完整日志存成 `<编号>.log`，「复制日志」直接进剪贴板，确认处理完可「删除」。

上传限制：

- 版本号三段或四段数字，可带 `-beta.1`；同一渠道版本号不能重复。
- 只允许 `UPDATESERVER_MAX_UPLOAD_BYTES`（默认 2 GB）以内的文件。
- 上传过程中失败或中断不会留下半成品记录，临时文件会自动清理。

## 4. 客户端配置

### 4.1 设置页

`设置 → 升级`：

- **服务地址**：`updates.example.com`、`192.168.1.20:8080`、`https://example.com/updates` 都可以；只填域名/IP 时按 `http://` 处理。不要带查询参数或 `#`。
- **渠道**：`stable` / `beta`。
- **启动后自动检测**：默认开启，只检测不自动下载。
- **检测时机**：启动后 1 / 3 / 5 / 10 / 30 分钟（默认 3 分钟）。
- 下方「检测与安装」显示当前状态（未配置 / 已是最新 / 发现新版本 / 无法连接 / 上次检测时间）与「立即检测」按钮；发现版本后按钮变为「查看升级」。

### 4.2 安装产物 `update.json`

打包时可以把默认地址写进安装目录，用户就不用手填：

```json
{
  "updateServiceUrl": "https://updates.example.com/zungmail",
  "channel": "stable"
}
```

打包命令：

```powershell
.\packaging\build-installer.ps1 -UpdateServiceUrl updates.example.com:8080
# 或者先改 packaging\update.json，填好 updateServiceUrl 后直接打包（脚本会复制模板）
.\packaging\build-installer.ps1
```

> `packaging\update.json` 默认地址为空；为空时打包脚本不会把 `update.json` 放进安装目录，
> 客户端会明确显示「未配置升级服务地址」，不会出现「有文件但没地址」的半配置状态。

优先级：**用户设置 > 安装目录 `update.json` > 未配置**。用户在设置里清空地址后会回落到 `update.json`。

### 4.3 手动检测入口

- 状态栏右侧的「新版本 vX.Y.Z」标识（只有发现版本 / 下载中 / 待安装时出现）
- `设置 → 升级 → 立即检测`
- 托盘右键菜单「检查更新」

## 5. 升级流程与数据安全

1. 自动检测在启动后 N 分钟执行，失败只写日志与状态，不弹窗。
2. 发现新版本：状态栏出现版本标识，托盘气泡提醒一次（遵循「新邮件桌面通知」开关）。
3. 用户点击标识 → 升级窗口展示版本号、更新说明、大小、发布时间、是否强制。
4. 点击「下载安装包」：下载到 `%LOCALAPPDATA%\ZungMail\updates\<版本>\<文件名>`，流式写临时文件 + 计算 SHA256，显示进度、可取消。
5. 校验：文件大小与 SHA256 必须与服务端记录一致，否则删除文件并提示重新下载；同版本已下载且校验通过时直接复用。
6. 「立即安装」：先保存写邮件草稿与设置，再启动安装程序并退出客户端（安装器自身也会 `taskkill` 兜底）。
7. **装完自动回来**：安装器在文件复制完成后自动重新启动 ZungMail，用户侧就是「点一下 → 自动关 → 装好 → 自动回来」，不用再手动点图标。
8. 覆盖安装：NSIS 使用注册表里的 `InstallLocation` 原地升级，只替换程序文件；卸载段才会在用户二次确认后删除数据目录。

### 5.1 便携版 zip 不算安装包

服务端允许上传 `.exe` / `.msi` / `.zip`，但客户端把 `.zip` 当**便携版**对待：

- 检测到便携版时，升级窗口顶部直接显示「这是便携版，需要手动解压」，大小那行标注「便携版 zip」，**不会**出现「立即安装」。
- 下载按钮变成「下载并打开文件夹」；下载完成（或本机已有校验通过的同名文件）后自动在资源管理器里选中该 zip，主按钮变成「打开所在文件夹」。
- 状态栏与设置页的状态文案是「便携版已下载，解压后覆盖程序目录即可」，不会出现「可以安装」。
- 便携版更新不影响 `%APPDATA%\ZungMail`：解压覆盖程序目录（默认 `C:\Program Files\ZungMail`，需先退出客户端并用管理员权限），或解压到任意目录直接运行 `ZungMail.exe`。

> 也就是说：想走「一键升级」就发 `.exe` / `.msi`；`.zip` 只适合手工分发或绿色版场景。

### 5.2 两种安装包的自动启动行为

| 安装包 | 客户端内「立即安装」怎么启动 | 装完是否自动拉起客户端 |
| --- | --- | --- |
| `.exe`（NSIS） | `/S` 静默安装 | 是。安装段末尾用 `explorer.exe` 转发启动 `ZungMail.exe`；静默模式下若程序文件没写进去，会弹窗报错并以退出码 1 结束 |
| `.msi`（WiX） | `msiexec /i <包>`（只用系统进度界面） | 是。`LaunchZungMail` 自定义动作在 `InstallFinalize` 之后执行，条件 `LAUNCHAPP=1 AND NOT REMOVE~="ALL" AND UILevel > 2` |

要点：

- 两种安装器都通过 `explorer.exe` 转发启动，客户端不会继承安装器的管理员令牌 —— 提权进程会被 UIPI 拦掉拖放（从其它邮件客户端拖邮件、往桌面拖附件都会失效）。
- **卸载不启动**（`REMOVE=ALL` 被排除）；**`msiexec /qn` 静默部署也不启动**（`UILevel=2` 被排除），适合组策略 / Intune 批量装。
- 连正常安装也不需要启动客户端时，加 `LAUNCHAPP=0`：`msiexec /i ZungMail-1.1.3-x64.msi LAUNCHAPP=0`。
- 手动双击 `.exe` 走向导时，自动启动交给「完成」页的「立即运行 ZungMail」复选框，不会启动两次。
- MSI **不做操作系统版本检查**：msiexec 的兼容模式会把 `VersionNT` / `WindowsBuild` 模拟成旧系统（曾导致 Win10 上弹「需要 Windows 10 1607 或更高版本」、装完没有 `ZungMail.exe`），现在只保留 64 位检查。

下载与安装相关的实现：

| 关注点 | 落点 |
| --- | --- |
| 地址解析与 `update.json` | `src/ZungMail.Infrastructure/Update/UpdateAddressResolver.cs` |
| 检测 / 下载 / 校验 / 错误分类 | `src/ZungMail.Infrastructure/Update/HttpUpdateService.cs` |
| 状态机与并发复用 | `src/ZungMail.App/Services/UpdateCoordinator.cs` |
| 启动后自动检测 | `src/ZungMail.App/Services/UpdateCheckScheduler.cs` |
| 安装引导 | `src/ZungMail.App/Services/UpdateInstallService.cs` |
| 升级窗口 | `src/ZungMail.App/Views/UpdateWindow.xaml` |
| 设置分区 | `src/ZungMail.App/Views/SettingsWindow.xaml`（升级） |

## 6. 状态与排错

| 现象 | 结果 / 原因 | 处理 |
| --- | --- | --- |
| 设置页显示「未配置升级服务地址」 | 用户设置为空且安装目录没有 `update.json` | 填地址并保存，或放入 `update.json` |
| 「地址不合法」 | 只支持 http/https，且不能带查询串/片段 | 改成 `http(s)://主机[:端口][/前缀]` |
| 「无法连接升级服务」 | DNS、连接被拒绝或 8 秒超时 | 检查服务是否启动、端口/防火墙、地址前缀 |
| 「升级服务返回 HTTP 404」 | 客户端地址指到了别的服务或子路径不对 | 用浏览器打开根地址确认管理页 |
| 「升级服务返回的内容不是有效的升级信息」 | 地址指向了普通网站/首页 | 确认填的是升级服务根地址 |
| 检测正常但没有新版本 | 版本不高于本地、渠道不匹配、版本仍是草稿 | 检查管理页「已发布」状态与渠道 |
| 「安装包校验失败」 | 下载被代理/杀毒篡改或上传后文件被替换 | 重新下载；核对管理页 SHA256 与服务端文件 |
| 自动检测没有发生 | 关闭了自动检测、地址未配置 | 设置 → 升级 检查开关与地址 |
| 上传 413 | 代理 `client_max_body_size` 或 `UPDATESERVER_MAX_UPLOAD_BYTES` 太小 | 调大限制 |
| 上传 409 | 同渠道版本号已存在 | 换版本号或先删除旧记录 |
| 升级窗口没有「立即安装」，只有「打开所在文件夹」 | 服务端这次发布的是便携版 zip，客户端不会自动安装 | 改发 `.exe` / `.msi` 才能一键升级；zip 需手动解压 |
| 装完后客户端没有自动起来 | `msiexec /qn` 静默部署、卸载、或显式传了 `LAUNCHAPP=0` | 正常安装/升级会自动拉起；静默部署请自行决定何时启动 |
| MSI 弹出「需要 Windows 10 1607 或更高版本」 | 旧版 MSI 用 `VersionNT` 判断系统版本，被 msiexec 兼容模式模拟成旧系统 | 换用 1.1.1 及之后的 MSI（只检查 64 位） |

日志：

- 客户端：数据目录 `logs/`（`AppLog`），升级相关关键字为「升级检测」「下载安装包」「升级检测失败」。日志按天一个文件（`app-yyyyMMdd.log`），**最多保留最近 7 天**（设置 → 通用 → 诊断与日志 可选 1/3/5/7 天），超期的在程序运行期间自动删除。
- 服务端：容器 `docker logs zungmail-update-server`，首次启动会打印数据目录与口令来源。

## 7. 发布一批新版本的推荐流程

1. 改 `Directory.Build.props` 的 `<Version>`（例如 `1.1.0`）。
2. 打包客户端：`.\packaging\build-installer.ps1 -UpdateServiceUrl <线上地址>`，产物在 `dist/`。
3. 打开升级服务管理页，上传 `dist\ZungMail-1.1.0-win-x64-selfcontained-setup.exe`，填写更新说明。
4. 发布前用一台测试机把服务地址指向测试服务，验证检测 → 下载 → 安装 → 数据仍在。
5. 发布。客户端下次启动（或手动检测）即可看到版本标识。

> 覆盖安装不会改动数据目录；如数据库结构有迁移，由客户端启动时 `DatabaseInitializer` 处理，迁移前会按既有策略备份。

## 8. 从 MailClient 升级到 ZungMail

1.2.0 起产品整体改名为 **ZungMail**（程序集、命名空间、`ZungMail.exe`、安装目录、数据目录、安装包名全部跟着换）。对已装 1.1.x `MailClient` 的机器，这是一次**原地升级**，运维不需要先卸载、也不需要搬运用户数据。

### 8.1 包名与产物

安装包命名由打包脚本决定，不是手填的：

| 产物 | 文件名规则 | 示例（1.2.0） |
| --- | --- | --- |
| MSI | `ZungMail-<版本>-x64.msi`（`packaging/build-msi.ps1`） | `ZungMail-1.2.0-x64.msi` |
| NSIS 安装包 | `ZungMail-<版本>-<运行时>-<flavor>-setup.exe`（`packaging/build-installer.ps1`，自包含时 flavor=`selfcontained`，`-FrameworkDependent` 时 flavor=`fd`） | `ZungMail-1.2.0-win-x64-selfcontained-setup.exe` |
| 便携版 | `ZungMail-<版本>-<运行时>-<flavor>-portable.zip` | `ZungMail-1.2.0-win-x64-selfcontained-portable.zip` |

`version` 来自 `Directory.Build.props` 的 `<Version>`（发 1.2.0 前先把它改成 `1.2.0`），或用 `-Version 1.2.0` 临时覆盖。版本号、包名、`SHA256SUMS.txt` 三者必须一致。

### 8.2 MSI：沿用原 UpgradeCode 原地升级

- `packaging/New-MsiSource.ps1` 里的 `UpgradeCode` 与 MailClient 1.1.x 完全相同（`{D2A9F5D4-6D7B-4F7A-9C2E-71B5E3A8C6F1}`），因此 Windows Installer 认定是**同一产品的升级**，走 `MajorUpgrade`：
  1. 先卸载旧的 MailClient 产品 —— 「应用和功能」里的旧条目、旧开始菜单组、旧桌面快捷方式、以及 `C:\Program Files\MailClient` 目录一起被移除；
  2. 再把 ZungMail 装进 `C:\Program Files\ZungMail`，重建开始菜单组与快捷方式，ARP 条目变成 `ZungMail <版本>`。
- 用户侧只需要运行新的 MSI（或由 Intune / 组策略 / `msiexec /qn` 下发），**不要**先手工卸载旧版，否则等于两装一遍。
- 升级完成后会自动拉起客户端（`LAUNCHAPP=1 AND UILevel > 2`）；静默部署不会拉起，由运维决定何时启动。
- 卸载仍然不动数据目录：`%APPDATA%\ZungMail` 与 `%LOCALAPPDATA%\ZungMail` 只在用户二次确认后才删除。

### 8.3 NSIS（setup.exe）：安装段自动清理旧 NSIS 安装

NSIS 的卸载信息键是 `HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\ZungMail`，本身没有跨产品升级逻辑，所以 1.2.0 的安装段显式做了旧版清理（`packaging/ZungMail.nsi` 里的 `LEGACY_*` 段）：

1. `taskkill /IM ZungMail.exe` 与 `taskkill /IM MailClient.exe`，两个进程都结束；
2. 若存在旧卸载键 `...\Uninstall\MailClient`：删除该键、删除开始菜单组 `MailClient` 与桌面 `MailClient.lnk`，并在确认 `C:\Program Files\MailClient\MailClient.exe` 存在时整目录删除旧安装目录；
3. `$APPDATA\MailClient` 与 `$LOCALAPPDATA\MailClient` **一律不碰**（里面可能还有用户数据备份）。

所以旧机是 NSIS 装的，直接跑新的 `ZungMail-<版本>-win-x64-...-setup.exe` 即可，不需要先手工卸载。**跨形态清不掉**：旧 MSI 装的机器请装新 MSI（或先卸载旧 MSI 再跑 setup），旧 NSIS 装的机器请装新 setup.exe（或先卸载旧 NSIS 再装 MSI）。

### 8.4 首次启动的数据接管

安装完成（或客户端自动重启）后，ZungMail 第一次启动会接管旧数据，规则如下：

| 旧数据位置 | 接管动作 | 耗时 |
| --- | --- | --- |
| 默认 `%APPDATA%\MailClient` | 整个目录**改名**为 `%APPDATA%\ZungMail`，不复制文件 | 同盘秒级 |
| 用户当年改过自定义目录（`location.json` 指向别处） | 只把新 `%APPDATA%\ZungMail\location.json` 的指针指向原目录，文件原地不动 | 瞬时 |
| 接管失败（旧目录被占用 / 权限不足） | 不再搬动文件，直接把新指针指到旧目录「原地接管」 | 瞬时 | 客户端正常启动、数据一条不少，但路径仍是 `%APPDATA%\MailClient`，之后不会再自动改名 |

前置条件与注意点：

- 接管只在「新目录还没有 `location.json`」且「旧目录（或旧 `location.json`）存在」时发生，所以**只能发生一次**；接管完成后新目录就有了指针文件，后续启动走常规分支。
- 改名成功后客户端会把 `mail.db` 里的绝对路径（附件、`eml`、内嵌图片的 `file://` URI）整体改写到新根目录，并删掉旧目录留下的空壳。
- 升级前请确认旧版 MailClient 已完全退出（托盘也退出）。旧版跑着会占用 `%APPDATA%\MailClient`，目录改名失败 → 走「原地接管」：功能不受影响，但数据仍留在旧路径。
- 新旧两版的单实例互斥名不同（各自带自己的产品名），**不会互相阻止启动**，两个进程同时操作同一数据目录有风险 —— 所以升级前务必先退出旧客户端。
- 接管不删除任何用户邮件：账户、邮件、标签、规则、模板、签名都跟着目录走。
- 接管结果会写一行启动日志：`旧数据目录已迁移：<旧路径> → <新路径>`，或 `接管旧版本的自定义数据目录（数据不搬动）：<目录>`，或 `旧默认目录搬不动（<原因>），原地接管：<目录>`。看到哪一行就知道走了哪个分支。

### 8.5 运维需要额外注意的点

- **ARP / 快捷方式**：MSI 走 `MajorUpgrade`，旧的「MailClient」条目与旧快捷方式由旧产品的卸载流程移除，新装自动生成 `ZungMail.lnk`；如果用户手工删过桌面图标，可在客户端 设置 → 关于 →「创建桌面快捷方式」补一个。NSIS 路径见 8.3，旧 NSIS 条目由新安装包自动清，跨形态需先卸载旧形态。
- **开机自启（注册表 Run 值）**：自启项由客户端写入 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值名从 `MailClient` 变成 `ZungMail`。首次启动会自动把旧值迁移成指向 `ZungMail.exe` 的新值（用户之前开着的自启继续有效），旧值随后删除，不需要运维手工清理。
- **升级服务里的旧版本记录**：`releases.json` 里的 1.1.x 记录可以原样保留，客户端检测只按版本号比较并取最高版本，不会因此误报。可选优化：把 1.1.x 下线，避免新装机的用户从 1.1.x 起装再升一次。
- **默认升级服务地址**：如果之前是靠安装目录里的 `update.json`（打包参数 `-UpdateServiceUrl`）给用户带默认地址，新版包要带**同样的参数**重打。用户自己在设置里保存过的地址存在数据目录 `settings.json` 里，接管后照旧生效（优先级：用户设置 > `update.json`）。
- **代码签名环境变量**：`packaging/sign.ps1` 现在优先读 `ZUNGMAIL_SIGN_THUMBPRINT` / `ZUNGMAIL_SIGN_PFX` / `ZUNGMAIL_SIGN_PFX_PASSWORD` / `ZUNGMAIL_SIGN_TIMESTAMP`，读不到再回退旧的 `MAILCLIENT_SIGN_*`，流水线可以按自己的节奏改名。
- **回滚**：退回 1.1.x 前先确认数据目录。新版已经把 `%APPDATA%\MailClient` 改名为 `%APPDATA%\ZungMail`，旧版不认识新目录，会当首次运行重新建库 —— 见 `docs/产品改名与数据迁移说明.md` 的回滚步骤。
