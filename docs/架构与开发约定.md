# 架构与开发约定

记录**当前生效**的结构与规则。历史上的评估、重构建议与逐条修复记录留在 `workdocs/`，这里只写结论。

## 1. 工程结构

```
src/
  ZungMail.Core            领域模型 + 抽象（仓储接口、服务契约、纯函数策略）
  ZungMail.Application     应用服务（跨仓储的业务编排：同步协调、规则、标签、跟进、清理…）
  ZungMail.Infrastructure  实现：SQLite 仓储、JSON 设置/模板、日志、升级、加解密、头像
  ZungMail.Mail            IMAP/SMTP 协议层（MailKit 封装、同步、MIME 映射、附件与正文）
  ZungMail.App             WPF 客户端（视图、视图模型、窗口、主题、托盘、启动装配）
  ZungMail.Update.Protocol 升级服务的共享协议契约
  ZungMail.UpdateServer    升级服务端（Minimal API）
tests/
  ZungMail.Tests / .UiTests / .UpdateServer.Tests
```

**依赖方向**：`App → Application → Core`、`App → Infrastructure → Core`、`App → Mail → Core`。Core 不引用任何上层；Infrastructure 与 Mail 互不引用，需要跨端协作时通过 Core 的抽象在 App 层装配。

## 2. 关键约定

### 2.1 写操作本地优先

标记已读、星标、移动、删除、打标签一律**先写本地库并立刻更新界面**，再异步回写 IMAP；失败的写操作进待同步队列，联网后重试。批量操作整批本地生效，一条服务器指令带走（不逐封建连）。

理由：货代现场网络不稳，用户不能因为一次超时就看到"操作失败但服务器已变"。

### 2.2 读操作分页与两段式加载

列表查询必须分页（`AppSettings.ListPageSize`，默认 100，10–500 兜底）；打开邮件先读本地邮件头（主题/发件人/附件名/业务单号）并立即上屏，正文与附件按需下载。**禁止一次性全量读取**。

### 2.3 数据库与迁移

- 单一 SQLite（WAL + FTS5），连接统一走 `SqliteConnectionFactory`。
- 结构变更：`Migrations` 连续版本 + `SchemaVersion`，每个迁移独立事务、用 `EnsureColumn` 做幂等；同步维护 `SchemaSql` 快路径；新增迁移必须配 `DatabaseMigrationTests`。
- 运行中的库不可直接复制（同步写入会报 `SQLite Error 8`），分析请停客户端或用只读连接。

### 2.4 策略集中在 Core 的纯函数里

判定类逻辑写成无副作用的静态类，便于单测与"改设置立刻生效"：`DisplayFormat`、`SearchQuery`、`PhishingDomainPolicy`、`StrangerSenderPolicy`、`LogRetentionPolicy`、`SignatureShareService` 等。渲染时算、不落库的判定（如仿冒域名）优先这样处理。

### 2.5 配置优先于硬编码

行为策略（预取窗口、折叠层数、保留天数、清理阈值、头像加载…）做成 `AppSettings` 设置项，放在「设置 → 通用」，给出可接受范围与默认值，并用 `EffectiveXxx` 夹取异常值。

### 2.6 后台任务

长跑任务用 `BackgroundService` 注册在 `App.OnStartup`，遵守两条：

- **首轮不要挤在启动关键路径上**：给首轮加延迟（日志清理 10s、头像 20s、清理调度 10 分钟节拍），把文件与网络操作让给首屏。
- **每轮现读设置**，改配置不需要重启。

### 2.7 界面

- 所有列表/卡片样式来自 `Themes/Controls.xaml`，右键菜单必须套 `MailContextMenu` / `MailContextMenuItem`，否则会退化系统白框。
- 颜色、字号、圆角一律走主题资源（`DynamicResource`），不写死色值。
- 含 WebView2 的编辑区不能放进 `ScrollViewer`，高度只能由外层 `Grid` 的 `*` 行分配。
- 图标容器不要固定 16×16（会裁掉 18px 图标），行高用 `Auto`。
- 跨窗口的资源不能引用别的窗口里定义的 `StaticResource`。

### 2.8 日志

- 位置：`%APPDATA%\ZungMail\logs\app-yyyyMMdd.log`，按天一个文件，**最多保留 7 天**（`LogRetentionPolicy` 夹取，`LogRetentionScheduler` 闲时清理）。
- 启动分段落日志（`StartupTrace`）：定位慢启动先看"启动环境"七行与"启动阶段"逐段耗时，再改代码。
- 日志行不得包含口令、授权码、完整邮件正文。

## 3. 验证要求（每一次改动）

| 项 | 标准 |
|---|---|
| 构建 | `dotnet build ZungMail.sln -c Release` **0 警告 0 错误** |
| 测试 | `ZungMail.Tests`、`ZungMail.UiTests`、`ZungMail.UpdateServer.Tests` 三套全绿 |
| 界面改动 | XAML 结构断言 + 真机截图验收；涉及滚动的改动要核对细滚动条与等高区块 |
| 触达真实服务器的操作 | 不可撤销的 IMAP 变更（移动/删除/批量标志）用单测 + 假会话验证，不拿真实邮箱做实验 |
| 数据安全 | 不得破坏真实数据目录；分析运行中的库需先停客户端或只读打开 |

## 4. 已知技术债（按影响排序）

1. `MainViewModel` 仍然偏大（列表、阅读、货代看板、批量处置集中在一个类），后续按"列表/阅读/货代/设置入口"拆分。
2. 业务模块的边界还是按技术分层切的，跨模块调用需要通过接口而非直接引用实现。
3. 日志单文件超过 5 MB 是截断重开而不是滚动归档，某天日志过密会丢前半段。
4. 静态 `AppLog` 与 DI 日志各持一个 `FileLoggerProvider` 写同一文件，极端并发下可能出现行交错。
5. 升级服务端是单机部署（SQLite + 本地存储），未做多实例与对象存储。

## 5. 扩展点

- **新协议能力**：在 `ZungMail.Mail` 加实现，通过 Core 抽象暴露给 Application。
- **新行业识别**：`FreightReferenceExtractor` 里的正则表 + `MailIndustryClassifier` 词表，新增类型补测试即可。
- **新后台任务**：`BackgroundService` + 首轮延迟 + 设置开关。
- **新设置项**：`AppSettings` 属性 + 「设置 → 通用」控件 + `EffectiveXxx` 兜底 + 迁移说明（若影响旧数据）。
