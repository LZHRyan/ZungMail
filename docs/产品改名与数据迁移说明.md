# 产品改名与数据迁移说明（MailClient → ZungMail）

适用版本：**ZungMail 1.2.0** 起。读者：实施 / 运维 / 开发。

三句话结论：

- 程序侧全部换名：解决方案、程序集、命名空间、`ZungMail.exe`、安装目录、数据目录、安装包名。
- 用户数据**不搬家**：首次启动 ZungMail 会自动接管旧版 `%APPDATA%\MailClient`，整个接管过程不删除邮件。
- 已装 1.1.x 的机器可以**原地升级**（MSI 沿用同一个 UpgradeCode）；回滚需要手工把数据目录名改回去，并优先用升级前的备份。

## 1. 改名范围清单

| 位置 | 旧（MailClient） | 新（ZungMail） | 备注 |
| --- | --- | --- | --- |
| 解决方案 | `MailClient.sln` | `ZungMail.sln` | 仓库根目录 |
| 项目 / 程序集 | `MailClient.App` / `.Application` / `.Core` / `.Infrastructure` / `.Mail` / `.Update.Protocol` / `.UpdateServer` | `ZungMail.*`（同名规则） | 测试项目：`ZungMail.Tests` / `ZungMail.UiTests` / `ZungMail.UpdateServer.Tests` |
| 命名空间 | `MailClient.*` | `ZungMail.*` | 全量替换，`XamlClass` 与 DI 注册同步 |
| 主程序 | `MailClient.exe` | `ZungMail.exe` | 任务管理器、`taskkill`、快捷方式目标都用新名 |
| 安装目录 | `C:\Program Files\MailClient` | `C:\Program Files\ZungMail` | MSI 与 NSIS 都按产品名生成 |
| 开始菜单 | 程序组 `MailClient`、`MailClient.lnk`、`卸载 MailClient.lnk` | 程序组 `ZungMail`、`ZungMail.lnk`、`卸载 ZungMail.lnk` | 每次安装重建 |
| 快捷方式文件 | `MailClient.lnk`（桌面 / 开始菜单） | `ZungMail.lnk` | 设置 → 关于 →「创建桌面快捷方式」也会用新名 |
| 卸载信息（ARP） | `HKLM\...\Uninstall\MailClient` | `HKLM\...\Uninstall\ZungMail`（NSIS）；MSI 由 `UpgradeCode` + `ProductName` 决定 | MSI 走 `MajorUpgrade` 自动替换；NSIS 1.2.0 安装段会主动清旧 NSIS 条目，见 §3.1 |
| 开机自启 Run 值 | `HKCU\...\Run\MailClient` | `HKCU\...\Run\ZungMail` | 首次启动自动把旧值迁移成指向 `ZungMail.exe` 的新值，无需用户重勾 |

| 单实例互斥名 | 旧进程自己的互斥名 | `Local\ZungMail.Desktop.SingleInstance.v1` | 新旧互斥名不同 → 不互相阻止，升级前必须先退出旧客户端 |
| 进程间激活通道 | `MailClient.ActivateListener` | `ZungMail.ActivateListener` | 二次启动只激活已有窗口 |
| 数据目录 | `%APPDATA%\MailClient` | `%APPDATA%\ZungMail` | 指针文件 `location.json`、`mail.db`、`eml\`、`logs\`、`settings.json`、`templates.json`、`avatars\` |
| 缓存目录 | `%LOCALAPPDATA%\MailClient` | `%LOCALAPPDATA%\ZungMail` | `updates\`（升级下载）、`WebView2\`（正文渲染缓存），可随时删 |
| 升级包名 | `MailClient-<版本>-...` | `ZungMail-<版本>-x64.msi`、`ZungMail-<版本>-win-x64-selfcontained-setup.exe`、`ZungMail-<版本>-win-x64-selfcontained-portable.zip` | 命名由 `packaging\build-msi.ps1` / `build-installer.ps1` 决定 |
| 版本号 / 产品属性 | `Directory.Build.props` 的 `Product` | `Product=ZungMail`，`Version` 递增到 `1.2.0` | 打包脚本读同一处 |
| 导出文件名 | `MailClient-backup-*.zip`、`MailClient-签名-*.json`、`MailClient-模板-*.json` | `ZungMail-*.zip` / `ZungMail-*.json` | 只影响新导出的文件，旧文件仍可导入 |
| 文档与离线教程 | 教程标题、`docs\` 内正文 | 一律写 ZungMail | 内置教程：`src\ZungMail.App\Assets\help\user-guide.html` |

**故意保留旧名、只做兼容读取的位置**：

- 代码签名环境变量：新名为 `ZUNGMAIL_SIGN_THUMBPRINT` / `_PFX` / `_PFX_PASSWORD` / `_TIMESTAMP`，`packaging\sign.ps1` 仍接受旧的 `MAILCLIENT_SIGN_*`。
- IMAP 集成测试环境变量：新名为 `ZUNGMAIL_TEST_*`，`ImapSyncIntegrationTests` 仍接受旧的 `MAILCLIENT_TEST_*`。
- 仓库物理目录 `D:\Code\MailClient`（与产品名无关，未做重命名）。
- 日志文件名格式 `app-yyyyMMdd.log` 与日志内容里的关键字（「启动环境」「启动阶段」）保持不变。

## 2. 旧数据接管规则

触发条件：**新目录 `%APPDATA%\ZungMail` 下还没有 `location.json`**，且旧目录 `%APPDATA%\MailClient`（或旧 `location.json`）存在。满足时客户端在打开任何数据库连接之前完成接管，之后不会再触发第二次（新指针已就位）。

| 旧数据放在哪 | 接管动作 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 默认 `%APPDATA%\MailClient` | 整个目录**改名**为 `%APPDATA%\ZungMail`，不复制文件；随后把 `mail.db` 里的绝对路径（附件、`eml`、内嵌图片 `file://` URI）改写到新根目录 | 同盘秒级 | 数据原地不动，只是一个目录名变了；旧目录空壳被清理 |
| 用户改过自定义目录（旧 `location.json` 指向别处） | 只写新指针 `%APPDATA%\ZungMail\location.json` 指向原目录 | 瞬时 | 文件完全不动，仍留在自定义目录 |
| 接管失败（目录被占用 / 权限不足） | 不再搬动文件，直接把新指针指到旧目录「原地接管」 | 瞬时 | 可用降级：功能与数据都正常，但路径仍是 `%APPDATA%\MailClient`，之后不会再自动改名 |

前提与注意：

- **升级前务必完全退出旧版 MailClient（含托盘）**。旧进程占着 `%APPDATA%\MailClient` 时改名会失败，客户端就走「原地接管」——邮件没丢、能用，但路径停在 `%APPDATA%\MailClient`。
- 新旧版本的单实例互斥名不同，不会互相阻止启动；两个进程同时操作同一数据目录有风险，所以还是要先退出旧版。
- 接管**不删除任何邮件**：账户、邮件、标签、规则、模板、签名都跟着目录（或指针）走。
- 接管结果写在启动日志里，看是哪一行就知道走了哪个分支：
  - `旧数据目录已迁移：<旧路径> → <新路径>`（默认目录改名成功）
  - `接管旧版本的自定义数据目录（数据不搬动）：<目录>`（自定义目录）
  - `旧默认目录搬不动（<原因>），原地接管：<目录>`（改名失败）
- 接管成功后 `%APPDATA%\MailClient` 就不存在了（已改名）。它还在的话，说明走的是「自定义目录」或「原地接管」分支，不是故障。

### 2.1 把数据挪到新路径（原地接管之后）

```powershell
# 1) 退出客户端（含托盘），确认没有残留进程
Get-Process ZungMail, MailClient -ErrorAction SilentlyContinue | Stop-Process -Force

# 2) 确认旧目录是数据本体，新目录里只有一个 location.json
Get-ChildItem "$env:APPDATA\MailClient" | Select-Object -First 5
Get-ChildItem "$env:APPDATA\ZungMail"

# 3) 删掉新目录里那份旧指针（它指向旧路径），再把旧目录改名过去
Remove-Item "$env:APPDATA\ZungMail" -Recurse -Force
Rename-Item "$env:APPDATA\MailClient" "$env:APPDATA\ZungMail"

# 4) 重新启动 ZungMail，设置 → 数据 里确认数据目录与账户数
```

自定义目录的情况不用搬文件，只要让指针指向原目录：`%APPDATA%\ZungMail\location.json`

```json
{
  "DataDirectory": "D:\\MailData"
}
```

## 3. 升级与回滚

### 3.1 升级前

1. 退出旧版客户端（托盘右键 → 退出），任务管理器确认没有 `MailClient.exe`；顺带确认没有杀毒软件正在全盘扫描数据目录。
2. 记一份基线（后面核对用）：账户数、邮件总数、文件夹数、标签数、规则数、模板数、签名数。
3. 备份：客户端 设置 → 数据 → 导出 ZIP；或停客户端后直接复制整个数据目录（**运行中不要复制 `mail.db`**，WAL 会让副本不一致）。
4. 用 MSI 下发最省事（同一 UpgradeCode，自动移除旧的 MSI 产品）。旧机如果是用 NSIS `setup.exe` 装的，直接跑新的 `ZungMail-<版本>-win-x64-...-setup.exe` 即可：安装段会结束旧进程、删除旧卸载键 `HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\MailClient`、旧开始菜单组、旧桌面快捷方式，并在确认 `MailClient.exe` 存在后移除 `C:\Program Files\MailClient`。**唯一清不掉的是跨形态**（旧 MSI ↔ 新 NSIS，或旧 NSIS ↔ 新 MSI），那种情况先从「应用和功能」卸载旧形态再装。
5. 开机自启不用手工清：首次启动会把旧的 `HKCU\...\Run\MailClient` 值迁移成指向 `ZungMail.exe` 的新值；如果用户已在新版里关掉自启，旧值也会被删除。

### 3.2 升级后核对数据完整性

先看界面：设置 → 数据 显示的数据目录应是 `%APPDATA%\ZungMail`；账户、邮件、标签、规则、模板、签名数量与 3.1 的基线一致。

需要更确切的数字时（**先退出客户端**，否则库被占用，只读打开也可能拿到旧快照）：

```sql
SELECT
  (SELECT COUNT(*) FROM accounts)    AS 账户,
  (SELECT COUNT(*) FROM folders)     AS 文件夹,
  (SELECT COUNT(*) FROM messages)    AS 邮件,
  (SELECT COUNT(*) FROM attachments) AS 附件,
  (SELECT COUNT(*) FROM mail_tags)   AS 标签,
  (SELECT COUNT(*) FROM mail_rules)  AS 规则,
  (SELECT COUNT(*) FROM contacts)    AS 联系人;
```

模板与签名不在数据库里，分别在 `templates.json` 与 `settings.json`（同目录），用编辑器的计数或直接看设置页即可。附件与内嵌图片的本地路径都已统一切到新目录，如果接管后正文图片大面积裂开，多半是曾经手工复制过目录导致 `mail.db` 里仍是旧前缀。

### 3.3 回滚到 1.1.x

```powershell
# 1) 退出 ZungMail，卸载（卸载时不要勾「同时删除数据」）
Get-Process ZungMail -ErrorAction SilentlyContinue | Stop-Process -Force

# 2) 数据目录改回旧名（1.2.0 已经把 MailClient 改名成 ZungMail）
Rename-Item "$env:APPDATA\ZungMail" "$env:APPDATA\MailClient"

# 3) 清缓存（可选，可丢）
Remove-Item "$env:LOCALAPPDATA\ZungMail" -Recurse -Force -ErrorAction SilentlyContinue

# 4) 重装 1.1.x
```

回滚要点：

- 当初是**自定义数据目录**的，文件没被动过，只需让旧版能找到指针：把 `%APPDATA%\ZungMail\location.json` 移到（或复制成）`%APPDATA%\MailClient\location.json`，内容指向原目录。
- **数据库结构只升不降**：`DatabaseInitializer` 看到库里的 `SchemaVersion` 高于代码版本时不会迁移、也不会报错，旧版就直接用新结构的库跑 —— 多数情况能读，但不保证。1.2.0 若升过结构，回滚请用升级前的备份 `mail.db`（连同 `eml\`）覆盖，别让旧版直接打开新库。
- 回滚后同样要清一次失效自启项与旧 ARP 条目（方向反过来：这次残留的是 `ZungMail`）。
